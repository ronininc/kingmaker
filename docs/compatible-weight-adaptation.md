# Compatible weight adaptation: bounded executable first slice

`python3 scripts/convert-compatible-weights.py SOURCE.safetensors NEW.safetensors --sha256 SOURCE_HASH`

This offline converter actually writes tensors, unlike `planForge`, which only produces a training plan. It supports F32/F16/F64 floating input to F16/F32, preserves names/shapes and supported integer/bool tensors, and keeps metadata. Unsupported encodings fail closed. It does not translate architectures, invent a tokenizer, train, merge incompatible models, convert GGUF quantization blocks, or admit/publish a model. The output is an unapproved precision candidate, not a claim of runtime compatibility or equivalent task quality.

Requires installed Python and NumPy. No downloads, pickle, source execution, network calls, credentials or model service changes. A hash pin is mandatory, output cannot overwrite files, malformed/overlapping/gapped data is rejected, nonfinite values/overflow/error-tolerance violations fail, and disk reserve is checked. Default maximum input/output 64 MiB, hard cap 256 MiB. Memory use can exceed file size during conversion; do not use as an unbounded large-model converter. The generic primitive requires separate architecture/operator/tokenizer validation and task benchmarks before use in a runtime. It is intentionally not automatically connected to model admission.

## Real bounded streaming execution proof (no downloads)

`scripts/prove-range-weight-execution.mjs SOURCE.safetensors NUMPY_REFERENCE.json` starts an ephemeral loopback-only range server over the existing checkpoint and closes it on completion. The client fetches only six 256-element output-head rows and its six bias values, verifies each range hash before execution, and accumulates the projection locally. It does not fetch or materialize the full checkpoint. The server uses bounded file reads, not a full-checkpoint memory buffer. Only the selected ranges are served.

Observed: 7 successful range requests, 6,168 weight bytes transferred from the existing 15,842,368-byte checkpoint; largest weight chunk 1,024 bytes. This chunk size is not a claim about total process RAM. All seven range hashes verified, an intentionally corrupted chunk was rejected, and an unselected range request returned 416. Independently generated NumPy F32 projection differed by at most 8.803642415067259e-8. Evidence is `weight-adaptation-evidence/streamed-projection.json` outside git. No external model downloads, no inference service, and no GPU were used.

This proves selected-weight streaming plus local numerical execution for one real projection layer. It does not establish streaming the complete Kronos model, attention/KV-cache handling, tokenizer behavior, an LLM, or an Ollama/GGUF runtime. It is a proof script, not yet a general production streaming runtime. Range hashes here are derived from a locally trusted existing source in the same process; production remote use requires an independently pinned/authenticated manifest rather than trusting hashes supplied alongside remote data. Local Python has NumPy and MLX but not Torch or the standalone safetensors package. The original full-model CPU implementation was not run or validated. No dependencies were installed.

## Full tokenizer forward: original architecture, actual streamed tensors

A subsequent deeper local search located the already installed original implementation in `ronin-osint/repos/Kronos` and its existing `.venv-kronos` environment (Torch 2.14.1, safetensors 0.6.2). The earlier dependency limitation applied only to default Homebrew Python; no packages needed installing.

`scripts/prove-kronos-tokenizer-streaming.py REPO CHECKPOINT CONFIG` now executes the complete original `KronosTokenizer.forward` on CPU with an eight-step synthetic numeric input. Its independent loading oracle is the standard safetensors full-checkpoint loader and unchanged original architecture. The streaming run starts with checkpoint parameters evicted to meta placeholders, fetches each module's required tensor ranges from an ephemeral loopback HTTP server, verifies each local-manifest hash, computes locally, and evicts that module's tensors after execution. Both reconstruction branches, quantization, indices and loss exactly matched the full-load oracle (all five maximum errors 0.0).

Actual result: all 96 checkpoint tensors used; 140 range requests because the decoder is reused by both branches; 23,722,432 bytes transferred; peak live checkpoint tensor payload 524,288 bytes; zero live checkpoint tensor bytes after forward, all parameters evicted. Streamed forward measured 0.077 seconds on this short input. This is NOT total process memory: activations, Python, Torch, allocator caches and server buffers are additional. The full-load oracle intentionally materializes the model as a separate validation step, then is deleted before the streaming run. The original small model is instantiated before initial eviction; this proof does not yet eliminate construction-time allocations.

This upgrades the proof from a single layer to a complete real tokenizer model forward. It does NOT prove the separate Kronos forecasting model, an LLM, a scene renderer, training or task quality. No external downloads, GPUs, model services, keys or project deployments were involved. It remains an architecture-specific validation script, not general production runtime integration. The reference shares the original architecture implementation, so this checks streamed loading/execution equivalence, not an independently reimplemented mathematical architecture. Evidence: `weight-adaptation-evidence/full-tokenizer-streaming.json`.

## Cold construction and forecasting-model extension

The latest script supersedes the earlier construction caveat: the streaming model now constructs all checkpoint parameters directly as meta tensors. For the tokenizer only, the original tiny derived nonpersistent quantizer buffer is constructed separately on CPU. Checkpoint tensors are not fully allocated during streaming-model initialization. The full-load oracle still intentionally runs first in the proof process, so its allocator footprint is included in the reported process RSS. Receipts now record SHA256 of checkpoint, config and both original architecture source modules.

`--forecast` selects the already installed Kronos-small model with its existing config/checkpoint, not a download. Its complete original `Kronos.forward` was validated using eight synthetic token/timestamp positions and deterministic teacher forcing. Both 1024-class logit heads exactly matched the standard full-load original architecture oracle (0.0 maximum difference). All 136 checkpoint tensors executed. 137 verified range requests transferred 101,063,936 bytes from the 98,980,656-byte checkpoint (one embedding reused); peak live checkpoint tensor payload was 2,101,248 bytes and zero after forward. CPU forward took 0.157 seconds in this run. Process RSS before streaming 435,765,248 bytes, after 439,943,168 bytes, process peak including oracle 455,081,984 bytes. These measurements explicitly do not claim a 2 MiB whole process.

Checkpoint hash: `b082dfcbd8e8c142a725c8bbb99781802f38fec81210e13479effb32b3c3e020`. Config hash: `5e0f6a605d5f81b5c9b559fe5cf716a1acb041c744e6f41bd05b097b7a685396`. Existing original repo commit `67b630e67f6a18c9e9be918d9b4337c960db1e9a`. Both tokenizer and forecasting variants were rerun after the changes.

This proves full architecture forward equivalence for this compatible forecasting model, not autoregressive forecasting accuracy, general LLM/Blender capability, trained new weights or production integration. The proof uses existing source and local trusted data only. Production gaps remain authenticated remote manifests, owner/source/config admission, robust cancellation/exception tensor eviction, preemptive memory/compute budgets and actual request routing. Hash receipts identify inputs; they are not a signature or independent trust anchor.

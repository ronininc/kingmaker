# Ronin Ownership, Kingmaker, and Solomon Architecture

Status: canonical ownership and product-boundary doctrine
Scope: Ronin Inc., Solomon, Kingmaker, Vault, customer enhancement requests, internal executive operations, capability creation

## Verdict

Ronin Inc. owns the ecosystem.

Solomon is Ronin Inc.'s flagship customer-facing orchestration product.

Kingmaker is Ronin Inc.'s internal administrative, executive, development, and capability-evolution system.

The Vault is the accumulated capability store produced by validated Ronin and community contributions.

Solomon consumes capability.

Kingmaker consumes and creates capability.


Ronin Inc. is the legal and strategic owner of the ecosystem.

Solomon is the public flagship.

## Product Boundary

### Solomon

Solomon is customer-facing.

Solomon exists to:

- orchestrate customer operations
- govern customer workflows
- execute approved actions
- consume Ronin/Vault nodes
- report reality
- preserve auditability
- expose diagnostics
- augment human operators

Solomon may consume nodes.

Solomon may run nodes.

Solomon may govern nodes.

Solomon may not create canonical nodes.

Solomon may submit enhancement requests to Kingmaker.

### Kingmaker

Kingmaker is internal to Ronin Inc.

Kingmaker exists to:

- manage Ronin operations
- manage customer enhancement requests
- manage Ronin workflows
- manage executive delegation
- consume Vault capabilities
- create new capabilities
- build software nodes
- build fabrication nodes when required
- coordinate CodaGen
- coordinate internal fabrication work
- validate builds
- prepare releases
- update repositories
- issue Ronin Inc. release notifications
- preserve founder intent
- operate as acting administrator when the founder is absent
- serve as founder command interface when the founder is present

Kingmaker is not a customer product by default.

Kingmaker is the internal administrative plane.

---

## Founder Presence Rule

When the founder is absent:

```text
Kingmaker = acting administrator
```

When the founder is present:

```text
Founder = active administrator through Kingmaker
```

The founder does not bypass Kingmaker.

The founder commands through Kingmaker.

Kingmaker remains the interface to Ronin's administrative plane.

---

## Kingmaker Authority Classes

### Green Class

Kingmaker may approve and execute without founder interruption when the request is useful, low-risk, and does not affect governance, IP exposure, customer privacy, revenue model, audit integrity, or constitutional doctrine.

Examples:

- common integrations
- quality-of-life improvements
- reports
- dashboards
- minor workflow improvements
- low-risk operational nodes
- routine bug fixes
- routine documentation
- broad-use customer support features

### Yellow Class

Kingmaker may investigate, prepare, prototype, and brief, but founder approval is required before canonization or release.

Examples:

- major new nodes
- fabrication support
- infrastructure expansion
- high-complexity workflow systems
- large domain packs
- large release candidates

### Red Class

Kingmaker must escalate immediately to founder review.

Examples:

- governance changes
- audit changes
- authority changes
- cross-tenant data visibility
- internal Solomon architecture exposure
- Ronin IP exposure
- privacy changes
- monetization changes
- Vault law changes
- constitutional changes
- security-sensitive requests
- liability-sensitive requests

Kingmaker may summarize Red Class requests, but may not approve them.

## Enhancement Request Flow

Customer-facing Solomon presents enhancement requests simply.

Recommended wording:

```text
Would you like to submit a Solomon enhancement request?

Enhancement requests are reviewed by the Ronin Inc. development team.
Approved requests may become available to eligible Solomon users through future updates.
No changes will be made to your system without review and approval.
```

Internal flow:

```text
Customer request
↓
Solomon enhancement request
↓
Kingmaker intake
↓
Risk classification
↓
Green / Yellow / Red routing
↓
Kingmaker approval or founder review
↓
Kingmaker build queue
↓
CodaGen / fabrication if required
↓
Testing and validation
↓
Repository integration
↓
Vault attribution
↓
Ronin Inc. notification
↓
Node download / auto-integration
```

Solomon does not build the node.

Kingmaker builds the node.

## Sovereign Build Preference

Kingmaker should not randomly connect external services when a capability can be reasonably recreated, owned, governed, audited, and maintained by Ronin.

Default preference:

```text
Build if ownership is practical.
Integrate only when ownership is impractical or low-value.
```

Preferred build examples:

- internal messaging
- task systems
- operational dashboards
- reporting systems
- workflow engines
- domain-specific operational logic

Preferred integration examples:

- global mapping datasets
- telecom delivery networks
- payment processors
- postal or government infrastructure
- extremely broad external identity ecosystems

The long-term direction is dependency reduction.

External dependencies should be periodically evaluated for replacement, internalization, or governed abstraction.

## Dual-Class Capability Doctrine

Capabilities are classified by primary beneficiary.

### Kingmaker Class

If the primary beneficiary is Ronin Inc., the capability receives Kingmaker treatment.

Examples:

- founder dashboard
- executive command app
- acquisition intelligence
- release governance
- internal fabrication control
- Ronin development tooling
- Kingmaker mobile

Kingmaker-class capabilities may remain internal, private, founder-controlled, and unavailable to customers.

### Solomon Class

If the primary beneficiary is customers, merchants, teams, operators, or organizations, the capability receives Solomon treatment.

Examples:

- scheduling
- inventory forecasting
- customer operations
- communications
- fabrication nodes
- domain workflows
- operational analytics

Solomon-class capabilities are governed, supported, customer-facing, and Vault eligible.

### Promotion Path

A Kingmaker capability may later become a Solomon capability if it becomes broadly useful to customers.

```text
Kingmaker internal tool
↓
Validated internally
↓
Generalized
↓
Solomon node
↓
Vault candidate
```

## Vault Contribution Doctrine

Community-requested capabilities that enter Canon become Vault capabilities.

Vault capabilities may not be separated from the Vault and resold as standalone functionality.

Users should never be financially punished for improving Solomon.

Ronin Inc. may monetize memberships, deployment, support, enterprise services, infrastructure, custom work, fabrication work, and adjacent products, but the original canonized community capability remains part of the platform for eligible users.

Core rule:

```text
If users help Solomon grow, Solomon grows for everyone.
```

---

## Contributor Credit

When a community-requested capability is released, Kingmaker should record attribution.

Attribution may include:

- originating company
- request category
- release date
- affected node
- Vault status

Customer-facing release notes may include a watermark or credit line when appropriate:

```text
Community Contribution
Originating Organization: [Company Name]
Released by Ronin Inc.
```

Credit does not imply ownership transfer, royalties, or control over the capability.

Credit exists to recognize contribution and strengthen ecosystem trust.

---

## Repair vs Alteration

CodaGen or Kingmaker repair mode may restore intended behavior.

Repair mode may not:

- alter governance
- expand authority
- weaken auditability
- expose internal systems
- create new capability without approval
- change constitutional doctrine
- change monetization rules

If a repair requires governance change, authority change, audit change, or constitutional change, it is not repair.

It is evolution.

Evolution requires Kingmaker classification and may require founder approval.

---

## Customer System Boundary

Customer Solomon instances may be configured.

They may not redefine Solomon.

Allowed:

- local settings
- workflows
- connectors
- domain configuration
- team permissions within allowed boundaries
- customer data structures

Not allowed:

- core governance modification
- audit deletion or weakening
- cross-customer visibility
- constitutional override
- internal Kingmaker access
- Ronin IP exposure
- unauthorized node creation

Founder absence must not mean Ronin absence.

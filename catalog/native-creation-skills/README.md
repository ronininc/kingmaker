# Actual native procedural creation skills

These three methods create new assets with original Kingmaker algorithms, without plugging in third-party generators, importing an asset library or downloading dependencies:

- `create-native-pbr-synthesis`: deterministic stone/noise, brushed-metal and checker surfaces; generates base-color, roughness, metallic, OpenGL normal and packed metallic-roughness PNGs.
- `create-native-lathe-mesh`: capped rotational geometry from bounded radius/height profiles, normals, UVs and indexed triangles; writes binary glTF.
- `create-native-textured-lathe`: composes those native algorithms into one GLB with embedded PBR textures and material bindings.

They execute via the reviewed conductor `native-asset-skill` handler and produce independently verifiable file receipts. They are staged rather than default-admitted. Parameter JSON schemas are inside each method so a governed colloquial planner can map a request to bounded inputs. The runtime must preserve an explicitly requested fidelity target; these implementations support procedural-proof only.

## Evidence and limits

Eight module tests pass: deterministic generated bytes, PNG decoding, GLB headers/buffer bounds/indices, resource/input bounds, real artifact writes/hashes, fidelity refusal and textured composition. A local Blender4.2.3 import test passed for generated mesh (152vertices/192triangles), all four individual material channels, and composed GLB with three embedded64x64 textures. This verifies parse/import compatibility, not aesthetic quality. No browser renderer, deformable character, human sculpt, rig, animation, full procedural material library or AAA photorealism is implemented.

Source implementation is `lib/native-asset-skills.mjs`; it uses Node standard-library primitives only. No proprietary provider code or assets were copied. Generated output rights are not reassigned or silently relicensed. Unlike external-asset admission, provenance states that no third-party assets were used.

## Reference versus implementation

`catalog/native-asset-methods` is now explicitly classified **reference-only**. Its35 website/tool workflow descriptions do not become native skills simply by existing as method files. New native implementations should live here, have real artifact tests and retain explicit limits.

The [Khronos glTF2 specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html) informs the interoperable file format: roughness is packed in green, metalness in blue, with embedded PNGs and buffer alignment. The algorithms here are original. [Khronos sample assets](https://github.com/KhronosGroup/glTF-Sample-Assets) have per-model license/credit records and are not copied or assumed CC0.

Additional suggested engines/libraries are references, not installed abilities: Three.js code is MIT but example media has its own licenses; pmndrs market advertises CC0 assets but source-code and asset rights differ; Needle commercial use requires a valid license. None is made a dependency by these skills. GPUOpen MatLib, Babylon, PlayCanvas and additional web material/renderer techniques still require source/rights review and actual implementation/testing before a native-skill claim.

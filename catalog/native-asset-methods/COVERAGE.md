# Native asset capability coverage

## Exact scope

35 authored method files cover14 named sources/tools. These are staged contracts, not an exhaustive inventory of every asset, shader, animation or UI operation on those changing websites. Asset libraries supply files; a method description does not recreate their geometry, textures or proprietary procedural graphs. No website catalogs or source implementations were copied. No downloads or installation occurred.

Sanctus documentation covers its broader ecosystem, so the three methods explicitly require proof that the exact operation/asset exists in the owner's Lite version. None assumes that all paid capabilities are free.

## What executes today

- `listNativeAssetMethods()` reads this inventory only.
- `prepareNativeAssetMethod()` can execute local byte/license-metadata admission and parameter preparation for five PBR definitions and one neutral-adult MPFB/Rigify definition. It returns **prepared-not-executed**, never a character/material render. Other definitions return **adapter-required**.
- Every conductor method currently reads job.json and records three declarations: admission, native operation, artifact review. All35 test as **incomplete**. No arbitrary model code or executable command is embedded.
- These files are not in the default catalog, not automatically admitted, not remotely published and not installed in the running app.

## Native generation path

The next implementation must bind explicit adapters to licensed local assets and pinned tools. MPFB can generate new characters from data, Rigify can generate rigs and Blender can construct new geometry/material graphs, but each needs real trusted code, tests and output inspection. Imported library assets must keep their provenance; they are not newly synthesized merely because Kingmaker chose them. Mixamo remains a hosted service, not a native offline generator.

For colloquial commands, the separate governed runtime should select capability IDs, validate JSON request parameters, preserve the user's quality target and order dependencies. It must report missing adapters and required authorization, not treat these templates as successful native execution. Keep the intent-to-plan tests distinct from live tool and quality evidence.

## Promotion gates

1. Exact per-file license/source review and provenance manifest.
2. Approved local tool versions, asset dependencies, bounded resource requirements.
3. Trusted adapter implementation; no implicit install/download/upload/login/payment.
4. Successful artifact-producing test plus independent receipt verification.
5. Task-specific visual/rig/material/animation tests and requested quality review.
6. Explicit admission and runtime integration. A draft method cannot self-promote by writing success metadata.

Fixture tests cover every method's incomplete behavior, metadata/schema consistency, preparation API, missing adapters and no default-catalog admission. No Cyberpunk-level quality, live character generation or full-site coverage is claimed.

# Writing a Method File That Survives Contact

A method file is written at the moment the method is proven, by the session
that proved it — not from memory a week later, and not before the first real
run, when it would be fiction with numbered steps.

Five contents make a method file survivable. The trigger: the situation the
method applies to, stated narrowly enough that a later session can tell
whether it is in that situation. The inputs: every value the steps need,
each with where it comes from — never "the usual credentials", always the
named source. The steps: ordered, each one action with its expected result
and the check that confirms it before the next step begins. The failure
table: each way the method has actually failed, the observable tell, and the
recovery — failures imagined in advance are marked as imagined. The proof:
the final end-to-end check that closes the method, graded with the fleet's
grade words.

Write for the reader who has none of your context: a fresh session, a
different brain, possibly a smaller local model. Anything the steps rely on
that is not in the file does not exist. If a step needs judgement the file
cannot carry, the file says so at that step and points at the training module
that governs the judgement — it does not silently assume a senior reader.
